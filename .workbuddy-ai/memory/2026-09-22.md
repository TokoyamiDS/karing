## 🔴 "It shows the Iran IP of me (direct) not the config" — the `scan-in` shadowing bug

The user's report, and the root cause is a **port collision that the app's own guard failed to
prevent**. Verified end-to-end, not inferred.

### Mechanism

Their settings had `mixed_port = 3068` **and** `scan_port = 3068` (they moved `mixed_port` off 3067 to
dodge the WinNAT reservation, and landed on the *default* scan port, which is not exposed in
Settings). The generated config therefore emitted **two inbounds on 3068**:

```
mixed-in            0.0.0.0:3068
mixed-forward-in    0.0.0.0:3066
scan-in             127.0.0.1:3068
```

and route rule 0 is `{"inbound": ["scan-in"], "outbound": "direct"}` — by design, so latency scanners
measure the physical NIC rather than the tunnel.

**The loopback binding is more specific, so it wins**: every client connecting to
`127.0.0.1:3068` is accepted by `scan-in` and routed **direct**. That includes the app's own
exit-IP lookups, which are exactly what populate the flag+IP label and the home outlet card.

### Proof (not inference)

Ran the core with the mixed/forward/control ports moved clear of the conflicts, then:

```bash
curl -x http://127.0.0.1:3068 https://api.ip.sb/geoip
{"region":"Tehran","organization":"Rightel Communication Service Company", ...}
```

That is the user's own Iranian IP, returned through the app's own lookup path. Confirmed.

### The guard was broken, which is the real defect

`setting_manager.dart:1400` already tried to prevent this:

```dart
if (scanPort == 0 || scanPort == mixedRulePort || scanPort == mixedForwardPort) {
  scanPort = kScanPortDefaultEffective;      // == 3068 — can still equal mixedRulePort!
}
```

Resetting to the default is not enough when the user has moved `mixedRulePort` **onto** that default.
**Fixed** by advancing until the port is clear of both mixed ports. Covered by
`test/scan_port_collision_test.dart` (4 tests, all passing): rule-port collision, forward-port
collision, zero, and the untouched case.

### Second, independent bug found on the way`ClashApi.getHttpRequestByProxy(port, tag, url)` **accepts `tag` and never uses it** — the request
goes to the mixed port and is routed by the rules, not by the outbound named in `tag`. So even with
the shadowing fixed, the per-node exit-IP label cannot target *that node*; it reports whichever node
`route.final` selects. **Not fixed** — the core exposes no "fetch a URL through outbound X" endpoint
(checked: `/proxies/{name}/delay` returns only a delay). Would need either a temporary selector switch
via `PUT /proxies/{name}` or a new core endpoint.

### Environmental conflict worth knowing

**adb (pid 6288) holds 3057 and 3066** — the app's `control_port` and `mixedForwardPort` — forwarding
to `:5555`. The core then dies with `bind: Only one usage of each socket address` (3066) and
`bind: An attempt was made to access a socket in a way forbidden by its permissions` (3057). The
`ANDROID_ADB_SERVER_PORT=6037` convention in my notes exists for exactly this class of collision.

## Probing technique that worked

Background launches from the agent session die (the fork error, and `&` is reaped). The
`windows-daemon-from-agent-session` skill applies. What actually worked for a **short** probe: start
the core with `&` inside the *same* Bash call, `sleep`, curl, then kill — but the core will only
survive if **every** port it binds is free, so move `mixed-forward-in` and
`experimental.clash_api.external_controller` to high ports first. A dying core is diagnosed by reading
its stderr, which names the exact port and reason.

## Follow-up: the same guard was missing for `controlPort`

Reading the whole guard block showed the pattern is uneven:

| port | guard |
|---|---|
| `mixedRuleNetSharePort` | reset if 0 |
| `mixedForwardNetSharePort` | reset if 0 **or** == `mixedForwardPort` ✓ |
| `scanPort` | reset + advance (my fix) ✓ |
| **`controlPort`** | **reset if 0 only — no collision guard at all** ✗ |
| `clusterPort` | reset if 0 only ✗ |

Two of the app's own listeners on one number means the core **cannot start**, and the bind error
reads like a permissions problem. The defaults are distinct, but a user who moves `mixed_port` lands
on another port just as easily as they landed on the scan port — which is precisely how this started.

Extended the guard to `controlPort` against all four of the mixed/scan ports, mirroring the scan
pattern (reset to default, then advance while it still clashes — because the default itself is not
safe once `mixed_port` has moved onto it). `test/scan_port_collision_test.dart` is now **6 tests, all
passing**; `flutter analyze` 0 errors.

**`clusterPort` left alone** — it is only used when clustering is enabled, which is off, and I did not
want to widen the diff without evidence it bites.

**Note the adb conflict is NOT fixed by this and cannot be**: adb's `forward` allocations take
arbitrary local ports (3057 and 3066 here) that the app has no way to predict. That remains an
environmental hazard to report, not something the guard can prevent.

## Latency concurrency cap raised to 30 on PC

User: *"make it have max workers for latency like 30 for max"*.

```dart
static int maxLatencyCheckConcurrency() {

}
```

Three things follow automatically, so **no other edit was needed**:

1. **The Settings picker is generated from the cap** —
   `for (var i = 1; i <= SettingConfig.maxLatencyCheckConcurrency(); i++) strings.add(...)`

2. **The field default is the cap** (`latencyCheckConcurrency = maxLatencyCheckConcurrency()`), so a
   fresh profile defaults to 30.
3. **Saved values are clamped to the cap** (`setting_manager.dart:2030`), so an out-of-range stored
   value can never exceed it.

**Mobile deliberately left at 10** — the PC/mobile split is a battery/thermal guard and the user is on
Windows. Not asked for, not changed.

**Their stored value is `latency_check_concurrency = 20`**, so it stays 20 until they pick 30 in
Settings → the concurrency picker. Raising the cap alone does not move an existing profile.

Verified: `flutter analyze` 0 errors on the three touched/related files; suite green apart from the

# 🔴 ROOT CAUSE of "the ports are always in use": the ephemeral range was widened to 1024

User: *"we must think about the ports problem, they are always in use."* They are, and here is why.

```
netsh int ipv4 show dynamicport tcp
  Start Port      : 1024
  Number of Ports : 13977          →  the ephemeral range is 1024–15000
```

**Windows' default is 49152–65535.** On this machine it has been widened down to **1024**, which
swallows the app's *entire* port band — `cluster 3050`, `control 3057`, `direct 3065`,
`forward 3066`, `rule 3067`, `scan 3068`, `netshare 4066/4067`, and the user's new `mixed 10808`.
**Any outgoing connection on the machine can be handed any of them**, at any moment.

That is the whole story behind the intermittent, wandering failures. Evidence gathered:

- **Dart bind test** (the same mechanism the app uses) on the live machine:
  `3050/3057/3065/3066/3067/3069 → 10013 WSAEACCES`; `3068/4066/4067/10808 → FREE`.
- `netstat` showed those ports as the **client end of ESTABLISHED connections to `127.0.0.1:5555`**
  owned by **`svchost.exe` pid 5952** — i.e. ordinary outgoing traffic had been *assigned* them.
  Nothing was listening on them. That is why they read as "in use" with no owner.
- Ports in **15001–49151 bind freely** (15400/15404/15408/20000/30000 all FREE). That band is outside
  this machine's range *and* outside the Windows default (49152–65535), so it is safe on both.

## Corollaries worth keeping

1. **My own scan-port guard is wrong in effect.** It advanced `scanPort` 3068 → **3069**, and
   3069–3168 is a WinNAT block, so the scan inbound still cannot bind. Advancing by one is not
   enough; the target band has to be chosen deliberately.
2. **The 10013-vs-10048 distinction matters.** An in-use port normally gives EADDRINUSE (10048);
   10013 (WSAEACCES) appears when the holder set `SO_EXCLUSIVEADDRUSE`, or when the port is in a
   reserved range. Do not read 10013 as "reserved" alone.
3. **`netsh int ipv4 show dynamicport tcp` is the first thing to check** for any "ports are always
   busy" report on Windows. The range is machine-specific and can be widened by tunnelling or VPN
   tooling.

## Proposed fix (presented to the user, not yet implemented)

Move the app's defaults into **15400–15407** — outside the ephemeral range on both configurations,
clear of the current WinNAT blocks, and clear of well-known service ports. Plus a runtime fallback so
a collision degrades instead of killing the core. **Caveat to raise every time:** changing the ports
invalidates anything configured against the old ones (the user runs AI agents with explicit
`HTTPS_PROXY` values), so this is a user decision, not a silent default change.
