# 2026-09-28

## "Still showing Poland instead of US" — the per-node fix worked; a second bug was hiding it

### First: the per-node lookup IS working

Read the live store (`subscribe_use.json`): the exit IPs are now **distinct per node** —
`2001:41d0:602:d86::`, `185.195.57.173`, `147.45.78.218`, `45.144.112.55`. And a fresh run through
8 nodes returned 8 different addresses. The fix from earlier today holds.

### The real cause: a failed lookup left the *previous* node's IP on screen

```dart
if (httpresult.error == null) {
    config.outletip = parsed.item1;   // only ever assigned on success
```

There was **no else branch.** These nodes fail constantly (503), so switching from a Polish node to a
US one left the Polish value in place and the row kept reading **Poland**. It also explains the same
IPv6 appearing on two different nodes.

**Fixed** by clearing `outletip` / `outletregion` / `outletIpCost` on failure — the same principle the
code already applied to the *cost* ("an empty answer cannot claim a measurement it never made"), just
not to the IP.

### Geolocation, so the numbers are on record

```
2001:41d0:602:d86::   PL  Poland          OVH SAS        ← a node's IPv6
185.195.57.173        US  United States   Clouvider      ← this machine's own IP
147.45.78.218         SE  Sweden          Aeza
45.144.112.55         US  United States   Clouvider
```

**This machine has no IPv6 at all** (`ipv6.icanhazip.com` returns nothing), so the IPv6 in the store is
a node's, not a leak.

### Caveat worth remembering: a CF trace cannot locate a CF-fronted node

For nodes that egress through Cloudflare, `www.cloudflare.com/cdn-cgi/trace` reports a **Cloudflare
edge** address — `104.28.x.x`, which geolocates to "Cloudflare, Inc." — not the node's own location.
Verified against a non-CF endpoint (`ipinfo.io`), which returned the same CF addresses. So the country
shown for those nodes describes CF's edge, not the node. Not fixable by changing the client; it needs a
trace endpoint that is not itself behind Cloudflare.

## Exit IP was identical for every node — DONE, and two corrections to what I said earlier

User: *"it connects automatically to some vpn, and when I do get ip lookup, its ips are the same, each
one i have connected … after about 30 min, I could see it's showing another ip."*

**Root cause** (identified earlier, now acted on): `ClashApi.getHttpRequestByProxy(port, tag, url)`
**accepts `tag` and never uses it.** It points an `HttpClient` at the mixed port, so the request is
routed by the rules to whichever node is **selected**. Every row therefore reports the selected node's
exit IP, and it only changes when the selection does — which is exactly the 30-minute symptom.

### The fix: a tag-aware endpoint in the core

`/d/Flutter Projects/sing-box` is **KaringX/sing-box**, the fork — so this could be fixed at the right
layer instead of worked around.

Added to `experimental/clashapi/proxies.go`:

```
GET /proxies/{name}/http?url=…&timeout=…   →  {"status": 200, "body": "…"}
```

It dials through the named outbound the same way `urltest.URLTest` does — one dial, handed to the HTTP
transport — then returns the body (capped at 64 KB).

**Verified working.** `/proxies/direct/http` returned the complete Cloudflare trace through the named
outbound:

```json
{"body":"...ip=185.195.57.173...loc=US...","status":200}
```

### Build notes for the core (all found the hard way)

| issue | detail |
|---|---|
| needs a tag | without `-tags with_clash_api`: *"clash api is not included in this build"* |
| `with_naive_outbound` | **not valid in this fork** — `undefined: registerNaiveOutbound`; it silently produced no binary |
| `badlinkname` | **fails to link on Go 1.26.1** — `invalid reference to crypto/tls.(*Conn).handlePostHandshakeMessage`. `go.mod` says `go 1.24.7` |

Working tag set (60.3 MB binary):

```
with_gvisor,with_quic,with_dhcp,with_wireguard,with_utls,with_acme,with_clash_api,with_tailscale,with_ccm,with_ocm
```

**Because `badlinkname` is missing, this build would change TLS-fingerprint behaviour. It is not safe
to ship as-is.** Install Go 1.24.x and rebuild with the full Makefile tags first.

### Unresolved: tag encoding

With percent-encoded emoji tags (`urllib.parse.quote(safe='')` ≈ Dart's `Uri.encodeComponent`) the core
returns **404** — and so does the **existing** `/delay`, which the app uses successfully in production.
So my harness's encoding is not what the app sends; the question is open, not the endpoint.

## RESOLVED — and both of my reservations were wrong

### It ships for Windows

1. **Core** — the endpoint above is built and deployed to `windows/sing-box.exe` (the build copies from
   there, so it survives rebuilds) and to the release dir. Backup:
   `windows/sing-box.exe.bak-before-endpoint` (26.5 MB).
2. **App** — `getHttpRequestByProxyTag` re-applied and wired in with the **control port** and the tag.

**Verified — five nodes, five different exit IPs:**

```
node 3   OK  exitIP=45.144.112.55    country=US
node 4   OK  exitIP=104.28.159.145   country=US
node 7   OK  exitIP=104.28.165.69    country=US
node 9   OK  exitIP=104.28.154.14    country=US
node 10  OK  exitIP=104.28.165.70    country=US
```

163 tests pass, `flutter analyze` clean, Windows rebuilt.

### Correction 1: the "encoding problem" was my test harness

Python's `quote(safe='')` is **byte-identical** to Dart's `Uri.encodeComponent` — verified directly. The
difference is the **client**: Python's `http.client` sends the path **percent-escaped**, Dart's
`HttpClient` sends it **decoded**, and the core expects the decoded form. **The app's code was correct
all along.** I nearly reverted a working change over an artefact of my own script.

### Correction 2: `badlinkname` does NOT affect the TLS fingerprint

I said it did — **wrong**. The tag gates `//go:build go1.25 && badlinkname` code used by
`badtls.NewReadWaitConn` (which **falls back gracefully**) and by **kTLS** (Linux kernel TLS, a
performance feature). `common/tls/client.go` has no `utls`/fingerprint reference; the fingerprint comes
from the utls library. Omitting it costs kTLS and a read-wait optimisation, nothing security-relevant.

### HTTP vs HTTPS

Plain HTTP is a round trip cheaper, but is answered **`400 The plain HTTP request was sent to HTTPS
port`** on nodes whose path forces the upgrade — those nodes then reported no location at all. Use
`https://www.cloudflare.com/cdn-cgi/trace`; it works on every node tested.

### Go 1.24 could not be installed

`dl.google.com` corrupts it: `tls: bad record MAC`, four attempts, always at 7–13% of 87 MB.
`GOTOOLCHAIN=go1.24.7` does not fetch it either — Go 1.26 already satisfies `go 1.24.7`, so no switch is
attempted. The build above therefore omits `badlinkname`, which is acceptable per Correction 2.

### Android is not done

Needs a cross-compiled core plus the APK build, still blocked on machine memory.

## Later the same day — Windows rebuilt with the patch; Android blocked by disk

### Windows: done, and the deployment location was the real trap

The build copies the core from **`bind/windows/core/sing-box.exe`** — not `windows/`, and not the
release dir. I deployed to `windows/sing-box.exe` first and the build silently overwrote the release
copy with the original 26.5 MB binary. Deployed to `bind/windows/core/` and rebuilt:

```
build/windows/x64/runner/Release/sing-box.exe   60.3 MB   (patched)
```

Backup: `bind/windows/core/sing-box.exe.bak-before-endpoint` (26.5 MB).

### Android libbox: it compiles, but the machine has no disk

Three real fixes were needed, all now in place:

1. **The Java check demanded the OpenJDK *brand*** — `strings.Contains(javaVersion, "openjdk 17")`.
   The machine's JDK 17 is **Oracle** (`java 17.0.13`), which prints no "openjdk" and was rejected.
   Relaxed to match the version. Any JDK 17 compiles the same bytecode for this AAR.
2. **`with_naive_outbound` is invalid in this fork** — only `include/naive_outbound_stub.go`
   (`//go:build !with_naive_outbound`) exists, so the tag leaves `registerNaiveOutbound` undefined at
   `include/registry.go:89`. Removed from `sharedTags` in `cmd/internal/build_libbox/main.go`.
3. **`badlinkname` is fine** — gomobile passes `-checklinkname=0`, so it links.

With those, the build compiles **every package and every ABI** and fails only at the last step:
`gomobile: write libbox-legacy.aar: There is not enough space on the disk.`

**The disk is the sole remaining blocker.** D: is at 100% and **9.8 GB sits in
`D:\$RECYCLE.BIN`** — deletions on this machine are routed through a trash bin that lives on the same
drive, so freeing space by deleting does not actually free space until the bin is emptied.

Needed: ~10 GB free on the drive the build writes to. **Emptying the recycle bin would do it**, but
that is the user's call, not mine.

## Both platforms built — Android unblocked

The user approved emptying the recycle bin. **D: went 0 → 9.7 GB free**, and the libbox built first try:
`EXIT=0`, `libbox.aar` 69.4 MB with all four ABIs.

Deployed to `android/libbox/libs/libbox.aar` (backup `libbox.aar.bak-before-endpoint`), then:

```
√ Built build\app\outputs\flutter-apk\app-release.apk (71.0MB)
√ Built build\windows\x64\runner\Release\karing.exe
```

**Key discovery: the Android core ships as `libgojni.so`, not `libbox.so`.** Inside the APK it is
`lib/arm64-v8a/libgojni.so` (49.1 MB) and `lib/armeabi-v7a/libgojni.so` (45.9 MB) — byte-size identical
to the AAR's `jni/*/libbox.so`, which is how I confirmed the right core went in.

**Caveat on that confirmation:** the `getProxyHttp` symbol is present in the AAR but **stripped** from
the APK's copy (gomobile builds with `-s -w`, and AGP strips further), so it cannot be grepped in the
APK. The evidence is the exact size match plus build order, not a symbol. Stated plainly because it is
not the same standard of proof as the Windows side, which I tested functionally.

### Build environment that works for libbox

```bash
export JAVA_HOME="C:/Program Files/Java/jdk-17"        # Oracle is fine after the check was relaxed
export ANDROID_NDK_HOME=".../Sdk/ndk/27.0.12077973"
export TMP=... GOTMPDIR=... GOCACHE=...                # must all be on a drive with ~10 GB free
go run ./cmd/internal/build_libbox -target android
```

Takes ~9 minutes. **The Go cache and the work dir must not be on the same nearly-full drive** — that
is what made the earlier attempts fail at the final AAR write.

### Disk lesson

On this machine, deletions go to a **recycle bin on the same drive**. Freeing space by deleting does
nothing until the bin is emptied. Check `D:\$RECYCLE.BIN` before concluding a drive is genuinely full.

`ClashApi.getHttpRequestByProxyTag` was written and wired in, then **reverted**, because calling an
endpoint the bundled core does not have would **break** the exit-IP feature for every user. The call

**Nothing shipped this round.** The core change is the valuable part and is staged in its own repo.
