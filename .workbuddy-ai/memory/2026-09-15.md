## Live connection test (proxy mode) — the app's real connection problem

Ran the core directly in proxy mode (no GUI, no TUN, no system proxy) using a copy of the user's `core_config.json` with the `tun` inbound stripped. Tested through the local mixed port only.

**ROOT CAUSE FOUND — the app cannot bind any of its ports.** `netsh interface ipv4 show excludedportrange protocol=tcp` shows the WinNAT dynamic reservation **3001–3100**, which contains *every* port the app uses: 3050 (cluster), 3057 (clash/control), 3066, **3067 (mixed/proxy)**, 3068 (scan), 3072 (html board). Direct bind test: all of them fail with `WinError 10013`; 3000 and 18067/28067 bind fine. The core therefore dies at startup with
`FATAL start service: start inbound/mixed[mixed-in]: listen tcp 127.0.0.1:3067: bind: ... access permissions`, so **proxy mode has no local port to connect through**. This is almost certainly the user's "problem connecting". Fixes: `net stop winnat && net start winnat` (admin, temporary — WinNAT re-allocates at boot), or move the app's ports outside 3001–3100.
- Note the app's own log had said `ready on 3067` at 11:11 the same day — the reservation is dynamic, so this breaks after a reboot with no config change.

**The nodes themselves:** with the ports moved to 18057/18066/18067/18068 the core ran fine.
- **US node WORKS** — VLESS + REALITY (`169.40.42.95:443`, `server_name: yahoo.com`, `xtls-rprx-vision`), clash delay ~438 ms, exit IP `45.144.112.55`, `loc=US`, colo EWR, TLS 1.3.
- **UK node is DEAD** — `188.220.67.181:2087` (VLESS + ws, no TLS): clash delay `504 Gateway Timeout`, request fails with `WinError 10054` (connection forcibly closed).

**"Best SNI" does not apply to this profile.** The US node is REALITY, and `_applySniSpoofing` skips REALITY outbounds — verified at `singbox_config_builder.dart:949`: `if (tls['enabled'] != true || tls['reality'] != null) continue;`. It also skips any node without a `transport`. So SNI Spoofing is a no-op for both nodes here, and the SNI scanner's template mode would refuse them (not CDN-backed). The tunable knobs for this node are the TLS fragment params (already set: sizes 5/94/1/109/1, delays 0/1, maxSplit 355) and DNS — not the SNI.

**DNS measurements** (all through the active tunnel, so treat as indicative): the two DoH resolvers the config uses as `final` for foreign domains — `120.53.53.53` and `1.12.12.12` (DNSPod) — answer in **~1.6–2.2 s**, which is slow and worth changing. UDP resolvers answer in ~1 ms, which is far too fast to be a real remote query: something local is intercepting :53 (the tunnel or the gateway), and they alternate between working and timing out (`94.140.15.15` failed one run, `94.140.14.14` the next).

**Measurement caveat — an unrelated VPN is active.** `xray_tun` (Wintun, ifIndex 17) holds the default route at metric 0, and `xray.exe` (PID 32776) owns the TCP connections to `169.40.42.95:443`. So Karing's outbound to its own node is itself tunnelled by that xray instance, and "direct" and "through Karing's proxy" both report the same exit IP `45.144.112.55`. The node is still genuinely in the path (switching the selector to the UK node changes the outcome from success to failure), but absolute latency numbers are inflated by the tunnel. Re-test with `xray_tun` disconnected for clean figures.

**Windows core is one commit behind.** `windows/sing-box.exe` reports `Revision: c394e591`, i.e. `c394e59`, not the fork's HEAD `a7eb0a7` — so it **lacks the `[6:2]` fragment-walk panic fix**. The Android core was verified separately; worth rebuilding the Windows core when convenient.
