# 🔴 "Works fast in v2rayN, not even connecting in Karing" — the missing WS `Host` header

User pasted a VLESS link: `…@172.67.216.37:8443?security=tls&sni=swz.yandex-api.store&fp=safari
&type=ws&path=%2Fassets`. Reproduced rather than reasoned about.

## Root cause

`AutoConfUtils._transportFromParams` set the WebSocket `Host` header **only when the link carried an
explicit `host=` parameter**:

```dart
if ((params['host'] ?? '').isNotEmpty) {
  tr['headers'] = {'Host': params['host']};
}
```

That link has no `host=` — only `sni=`. **v2rayN/Xray default the Host to the SNI; we did not**, so
sing-box sent the dialled IP as `Host`. On a Cloudflare-fronted node that is fatal: **Cloudflare routes
by Host**, so the WebSocket upgrade is answered **403** and the node never connects.

## Measured, not assumed

Built the same outbound as a standalone sing-box config and ran the real core against the real node:

| `Host` sent | result |
|---|---|
| `swz.yandex-api.store` (the SNI) | **503** — reached Cloudflare, origin down |
| the dialled IP (our behaviour) | **403** |
| the IP explicitly | **403** |

Fingerprint made **no** difference (safari / chrome / none all behaved identically), which ruled out a
uTLS theory before it cost anything. A direct probe of the SNI returned **521** and the WS path
**503** — so the node's origin is **down right now**, meaning even v2rayN would fail at this moment.
That does not weaken the diagnosis: the 403 happens **regardless** of origin health, so Karing would
have failed even while v2rayN was working.

Also worth knowing: `swz.yandex-api.store` resolves **IPv6-only** (`2a06:98c1:3122::`, CF), so the
IPv4 in the link is a user-supplied clean edge address — normal for this kind of share.

## Fix

Default the host to the SNI (`sni`, falling back to `peer`) when `host=` is absent, applied to **all
three** transports that use it — `ws`, `httpupgrade`, and `h2`/`http`. An explicit `host=` still wins,
and a link with neither sets **no** header, because inventing one would be worse than omitting it.

`test/ws_host_header_test.dart` — **4 tests pass**, one of them built from the user's exact link.

Suite: **142 pass + 1 harness load-flake** (passed on first retry); `flutter analyze` 0 errors.

## "Still not connecting" — the parse-time fix never reached the stored node

The WS Host fix was applied at **parse time**, and this node was imported **before** it existed. The
parsed result is **persisted**, so the node keeps its old raw forever.

Verified in the user's own profile rather than assumed — `subscriptions.json`, group `china`:

```
tag: 👉🆔@v2ray_configs_pool📡🇨🇦®️C
raw: {"type":"vless","server":"104.25.77.78","server_port":8443,
      "transport":{"type":"ws","path":"/assets"}, "cf":true}
has Host header: False
```

**39 of 41 stored ws nodes carry a Host. This was the 1 that didn't.** (Note the address had also
rotated from `172.67.216.37` to `104.25.77.78` — the app's CF IP rotation — while the transport still
lacked the header.)

### Fix: repair in place, do not ask for a re-import

Added the same SNI→Host default to **`SingboxConfigBuilder.normalizeConfigCompatibility`** — the
existing *"Final safety net for imported/persisted profile data"* — which runs on the **fully assembled
config** immediately before it is written (`vpn_service.dart:370`). So already-persisted nodes are
repaired on the next start, with no subscription refresh and no re-import.

An existing `Host` is never overwritten and sibling headers survive; a ws node with **no SNI** still
gets no header, because there is nothing to default to.

### The node itself is still down

`521` from Cloudflare via **both** `172.67.216.37` and `104.25.77.78` — the origin is unreachable. So
it will keep failing until the node recovers, **regardless of client**. Worth telling the user to
re-test the same node in v2rayN right now: if v2rayN also fails, that confirms it is the node, not us.

### Lesson

**A parse-time fix does not reach data that was already persisted.** When the parsed result is cached,
the fix has to live (also) where the data is *consumed* — here, the config builder's safety net, which
already existed for exactly this class of problem.

## Lookup times read too high (lowest 1.2s against a 400ms ping)

Investigated by reading the code and measuring, not by guessing. Three findings, one of which is the
real problem.

**1. The lookup is not per-node at all — this is the headline.** `ClashApi.getHttpRequestByProxy(port,
tag, url)` **accepts `tag` and never uses it**: it points an `HttpClient` at the mixed port, so the
request is routed by the **rules** to whatever node is **selected**. Every row therefore reports the
*selected* node's cost, which is exactly the uniform floor the user is seeing. Same root cause as the
per-node exit IP: there is no tag-aware way to fetch a URL through a named outbound.

**2. Every lookup is a cold connection.** `getHttpRequestByProxy` builds a **new `HttpClient()` per
call**, so each reading pays the full handshake to the node *and* TLS to the target. It measures
handshake + request, not round-trip — which is why it can never look like a ping.

**3. The endpoint was heavy and over TLS.** `https://api.ip.sb/geoip` — 391 bytes of JSON, over TLS.
**Switched to `http://www.cloudflare.com/cdn-cgi/trace`** — 201 bytes, served from Cloudflare's edge,
and **plain HTTP on purpose**: over a high-RTT node, skipping the TLS handshake saves a whole round
trip, which at ~400ms RTT is most of the excess. Verified live: returns `ip=37.156.154.81` and
`loc=IR` — the two facts needed, nothing else.

Parsing extracted to `NetworkUtils.parseOutletIpBody` (trace | legacy JSON | bare address) with four
tests, because a slip there silently blanks the location for every node.

**Not fixed, and honest about it:** per-node attribution still needs the tag-aware core endpoint.
Until then the column measures the selected node, and that should be said plainly rather than
presented as a per-node figure.

**Also unexplained:** the 400ms-vs-140ms ping gap. The app's default test target is
`kUrlTestList[0]` = `https://www.gstatic.com/generate_204`, the same one v2rayN uses, so the target is
**not** the difference. Not chased further this round.

`outlet_location_test.dart` — **13 tests pass**. `flutter analyze lib/` 0 errors. Suite green modulo the
known load flake (`dns_routing_test.dart`, passed on first retry). `network_utils` had to be imported
into `server_manager.dart` — the analyzer caught the omission that the tests did not.

## Fixed: the lookup cost was frozen at the first reading

The exit-IP lookup was guarded by `if (settings.latencyCheckResoveIP || config.outletip.isEmpty)` — so
once an address was known and that setting was off (the default), **every later latency check skipped
it**. The displayed cost therefore described a measurement from some earlier session and re-testing
never refreshed it, which is exactly what the user reported.

Now it runs on **every successful latency check**: one small request per node per test, the same order
as the latency probe itself. `latencyCheckResoveIP` keeps its meaning for the address; the cost is
simply always fresh.
