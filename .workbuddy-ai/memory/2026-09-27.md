# 2026-09-27

## "Update All" added to the servers list

User: *"add update all profiles inside the servers list."*

### It already existed — just on the other screen

The app already had the whole mechanism in **`my_profiles_screen.dart`**:

- `_buildHeaderUpdateAllButton(tcontext)` — a `cloud_download_outlined` icon, or a spinner with a
  live count while refreshing
- `onTapReloadAll()` → `ServerManager.reloadAll()`
- `_reloadingAllCount()` — counts remote groups where `ServerManager.isReloading(groupid)`

The **server-select screen** had only the latency test (`Icons.bolt_outlined`) and the settings gear in
its header. So this was a port, not new machinery — worth checking first, and it kept the two screens
consistent rather than inventing a second pattern.

### What was added to `server_select_screen.dart`

- `_reloadingCount()`, `onTapUpdateAll()`, `_buildUpdateAllButton(tcontext)` — deliberately mirroring
  the profiles-screen versions, including the count-in-spinner behaviour.
- Placed **next to the latency test** in the header row.
- Header title width `windowSize.width - 50 * 3 - 26` → `- 50 * 4 - 26`, because the row now has four
  50px slots: back, latency test, update all, settings.

### The non-obvious part: nothing repaints on reload

Latency tests fire `onEventTestLatency`, which the screen already hooks. **A subscription reload fires
no such event**, so a spinner and count would have frozen at their first frame. The 1-second repaint
timer now also fires while a reload is in flight:

```dart
if (_rePaint || _reloadingCount() > 0) {
  _rePaint = false;
  setState(() {});
}
```

It stops on its own once the count reaches zero.

### No new translation keys

Reused `meta.update` + `meta.profile` for the tooltip — the same strings the profiles screen uses.

Verification: `flutter analyze lib/` **0 errors**; full suite **163 pass** (first run hit the known
load-harness flake, passed on retry). Windows and Android both rebuilt.

## Android build is blocked by machine memory — not by the code

Windows built clean (`√ Built karing.exe`, 88.3 s). **Android failed repeatedly** with:

```
Gradle build daemon disappeared unexpectedly (it may have been killed or may have crashed)
```

Not a code error. Fresh JVM dumps in `android/hs_err_pid*.log` told the real story:

```
# There is insufficient memory for the Java Runtime Environment to continue.
# Native memory allocation (mmap) failed to map 2097152 bytes. G1 virtual space
# Native memory allocation (malloc) failed to allocate 1611856 bytes. Chunk::new
```

**It could not allocate 2 MB, then 1.6 MB.** The machine was down to **3.8 GB of commit free of
35.5 GB**, while the Gradle JVM alone wants ~3 GB (2 GB heap + 1 GB metaspace).

Top consumers at the time: Memory Compression 1.5 GB, `dart` 1.4 GB, **Devin 1.0 GB**, `vmmemWSL`
545 MB, Chrome 481 MB, WorkBuddyAI ×2 ~700 MB.

Lowering the heap from `-Xmx3072M` to `-Xmx2048M` did **not** help — the machine was too far gone for
any reasonable Gradle config. **The fix is to free memory, not to keep tuning the JVM.**

Both `gradle.properties` files are now at a sane, consistent baseline:

```
org.gradle.jvmargs=-Xmx2048M -XX:MaxMetaspaceSize=1024M -XX:ReservedCodeCacheSize=256M ...
kotlin.compiler.execution.strategy=in-process
```

**Rule: an Android release build on this machine needs roughly 3–4 GB of free commit.** Check
`Commit free` before starting one; if it is under ~5 GB, close something first. The earlier successful
builds ran at 10.9 GB free.
