## Android release build unblock (in progress)

### Root cause of the Gradle/Kotlin build failures
Memory pressure on this machine is a **pagefile commit-limit** problem, not a physical-RAM problem.

Measured facts (not guesses):
- Physical RAM: 24,313 MB total. Pagefile `C:\pagefile.sys`: fixed **8192 MB**, `AutomaticManagedPagefile=False`.
- => Windows commit limit ≈ 24.3 GB + 8 GB ≈ **32.5 GB**, with only ~8 GB free commit at idle.
- Crash log `android/hs_err_pid25308.log`: `Native memory allocation (mmap) failed to map 65536 bytes.
  Error detail: Failed to commit metaspace` — command line was
  `org.jetbrains.kotlin.cli.jvm.K2JVMCompiler @...` running **inside the Gradle JVM**
  (`kotlin.compiler.execution.strategy=in-process`).
- Second log `hs_err_pid15140.log`: `failed to map 398458880 bytes (G1 virtual space)`.
- The pagefile is NOT full (`CurrentUsage` 103 MB, `PeakUsage` 113 MB). Both crashes fail at the
  **commit limit**, which is why "free RAM" looked healthy while builds still died.

### Fixes applied
`android/gradle.properties`:
- Removed the broken quoted `kotlin.compiler.execution.strategy="in-process"` (the value must be bare).
- Set `kotlin.compiler.execution.strategy=out-of-process` so a Kotlin OOM can no longer kill the build.
- `-XX:MaxMetaspaceSize` 1024M -> 768M, added `-XX:ReservedCodeCacheSize=192M` on `org.gradle.jvmargs`.
- Kept `org.gradle.daemon=false`, `org.gradle.parallel=false`, `kotlin.incremental=false`.

`android/app/build.gradle.kts`:
- Added, after `flutter { source = "../.." }`:
  `tasks.withType<org.jetbrains.kotlin.gradle.tasks.KotlinCompile>().configureEach { compilerOptions.freeCompilerArgs.addAll("-J-Xmx1536M", "-J-XX:MaxMetaspaceSize=512M") }`
- Rationale: KGP only honours `kotlin.daemon.jvmargs` when a Gradle daemon is used; this project runs
  with `org.gradle.daemon=false`, so the forked compiler JVM's heap must be pinned via freeCompilerArgs.

Freed ~1.9 GB of disk by deleting `build/windows` (1.67 GB), the 109 MB `.cache.dill.track.dill`, and
`build/test_cache` + `build/unit_test_assets`. These are regenerable; C: had only 17.7 GB free.
D: drive has 1.9 GB free and E: 0.9 GB — the reason the pagefile cannot simply be grown on C: is NOT
space; it is that raising it requires an admin, reboot-level change to system config.

## Update — build progressed; three further blockers found

The memory fix worked. `flutter build apk --release` now compiles Kotlin instead of crashing the JVM.
Reaching `:app:compileReleaseKotlin` proved the compiler survives. Remaining blockers, in the order
they surfaced:

### 1. `Could not find :libbox:.` — FIXED (in `D:/Flutter Projects/vpn-service`)
`vpn-service/android/build.gradle` had `implementation(name: "libbox", ext: "aar")` resolved via
`flatDir { dirs 'libs' }`. That `libs` is **relative to `rootProject`**, which for a Flutter app is
the *host* `android/` dir — so Gradle searched `<host>/app/libs/libbox.aar` and failed, even though
the AAR sits in the plugin's own `android/libs/`.
Fix: `implementation files("libs/libbox.aar")` — unambiguous, host-independent.

Also discovered: the fork carries a **stray `android/libbox/` Gradle module** (tracked in git) whose
`build.gradle.kts` publishes `libs/libbox.aar` under empty coordinates `:libbox:`.
Upstream `main` has `include(":libbox")` in `android/settings.gradle.kts` **but no `android/libbox/`
directory at all** — so upstream's include is vestigial. The fork's added module is what made `libbox`
resolve to a bogus coordinate. Its AAR is byte-identical (same MD5 `1a5effcd…`) to the plugin's copy,
so it is pure duplication. **Not yet removed — flagged to the user** (tracked file).

### 2. Kotlin `unresolved reference 'len' / 'next'` in the plugin — FIXED
`KaringVpnService.kt` (openTun) looped over `options.getDNSServerAddress()` as if it were a
`StringIterator` using `dns.len()` / `dns.next()`.
Ground truth from the libbox bindings + `D:/Flutter Projects/sing-box/experimental/libbox/tun.go`:
`GetDNSServerAddress() (*StringBox, error)` — a **single** address (tun IPv4 base + 1, e.g.
`172.19.0.1/30` -> `172.19.0.2`), nil when no spare IPv4. It is not an iterator.
Fix: `dns?.getValue()` + single `addDnsServer(...)` guarded by `isNullOrEmpty()`.
All other iterator uses in that file (`hasNext()`/`next()` on `RoutePrefixIterator`/`StringIterator`)
were already correct — this was the only stale call.

### 3. `unresolved reference 'nebula'` in the APP's Kotlin — **BLOCKED, needs a user decision**
`android/app/src/main/kotlin/com/nebula/karing/{TileService,AutomationCommandReceiver}.kt` reference
`io.nebula.vpn_service.VpnServiceImpl` (`ACTION_START`/`ACTION_STOP`/`ACTION_RECONNECT`/`ACTION_STATE`/
`ACTION_START_RESULT`/`ACTION_STOPED`), `VpnState` enum, `getCurrentState()` and `service_file_name`.
The plugin on disk provides **none** of these:
- package is `com.nebula.vpnservice` (not `io.nebula.vpn_service`),
- it exposes a Flutter MethodChannel pair `plugin_karing_vpn_service` /
  `plugin_karing_vpn_service_event`, driven by the `VPNState` object,
- `KaringVpnService.onStartCommand` is bare — no Intent actions, no `VpnServiceImpl`, no `VpnState`.
These two app files are **upstream, unmodified** (byte-identical to `upstream/main` and
`refrences/karing`), and both are declared in `AndroidManifest.xml` (Quick Settings tile +
automation intents) — live features, not dead code.
The plugin's Dart side (`vpn-service/lib/src/vpn_service.dart`) uses the same MethodChannel names as
the plugin's Kotlin, so the **plugin is internally consistent**; the mismatch is between upstream's
app Kotlin and this generation of the plugin. This cannot be reconciled by a package rename alone.
Needs a decision: add a compatibility `VpnServiceImpl`/`VpnState` Intent surface to the plugin, or
port the two app Kotlin files to the channel API.
`android/app/build.gradle.kts` was left **unchanged** after removing an invalid `-J-Xmx1536M`
freeCompilerArg (`-J` is a JVM launcher flag, not a kotlinc arg; `out-of-process` already routes JVM
options via `kotlin.daemon.jvmargs`).

### The libbox fix had to be redone — `files()` was wrong
`implementation files("libs/libbox.aar")` fixed resolution but broke the AAR build:
`Error while evaluating property 'hasLocalAarDeps' of task ':vpn_service:bundleReleaseAar'` —
AGP forbids **direct local .aar** deps when the project is itself built as an AAR.
Correct fix (kept): keep the coordinate form `implementation(name: "libbox", ext: "aar")` and point
flatDir at the plugin's own dir via an absolute path captured at configuration time:
```groovy
def pluginLibsDir = file("libs").absolutePath
rootProject.allprojects { repositories { flatDir { dirs pluginLibsDir } } }
```
This is the only form that both resolves and survives `bundleReleaseAar`.

## Android RUNTIME startup bug — user report: "lost its profile, only quit/website buttons"

The screen is `lib/screens/launch_failed_screen.dart` — the only UI with `meta.website` +
`meta.quit` buttons. `invalidProfile` renders as
"The app failed to start [Failed to access the profile], please reinstall the app".

### Cause 1 (the reported bug): no Android branch in `profileDirNonPortable()`
`lib/app/utils/path_utils.dart` `profileDirNonPortable()` had Windows + Linux branches then
`return ""`. Its only other path was `FlutterVpnService.getAppGroupDirectory(...)`, which the local
plugin hardcodes to `return null` (`vpn-service/lib/src/vpn_service.dart:334`).
`AppUtils.getGroupId()` returns `group.com.nebula.karing` — an **iOS App Group id**, so that hook is
Apple-only and Android was simply never wired.
Chain: getAppGroupDirectory -> null -> no Android branch -> `""` -> `profileDir() == ""` ->
`main.dart:158` sets `invalidProfile` -> LaunchFailedScreen.
Everything else derives from `profileDir()` too: `cacheDir`, `profilesDir`,
`serviceConfigFilePath` (= profileDir/service_core_config.json),
`diversionTemplateConfigFilePath`, AutoUpdateManager's file path.

Fix: added an `if (Platform.isAndroid)` branch using path_provider's
`getApplicationSupportDirectory()` (== Android `getFilesDir()`), plus
`import "package:path_provider/path_provider.dart";`. path_provider 2.1.6 is already a direct
dependency and `main.dart` already imports it. `flutter analyze` on the file: No issues found.

### Cause 2 (latent — would have hit immediately after Cause 1): wrong version units
`vpn-service/.../VpnServicePlugin.kt` returned `Build.VERSION.RELEASE` ("13", "14", …) for
`getSystemVersion`, but `main.dart:213-217` does `int.tryParse(version)` then `v < 26` alongside the
message "Minimum required: >= 8.0" — i.e. it expects the **API level** (26 = Android 8.0).
Any device whose release string parses to 9..25 would falsely abort with `systemVersionLow`.
Fix: return `Build.VERSION.SDK_INT.toString()`.
