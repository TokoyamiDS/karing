## DNS: "resolve via the connected profile" was silently a no-op — fixed

User report: *"the dns settings are mostly missing, i want to make the domain resolver be the config(profile) connected"*, and on being asked whether it should be optional: *"it was there, there was something problem and app has disabled it automatically"*.

**Root cause.** `SettingConfigItemDNSProxyResolveMode.proxy` only changed *which* DNS server answered — `dns()` in `singbox_config_builder.dart` did:
```dart
} else if (resolveMode == ...proxy) {
  rules.add({'inbound': ['tun-in'], 'server': remoteServerTags.first});
  final_ = remoteServerTags.first;
}
```
and `_dnsServerFromUrl()` never emitted a `detour`, so the query still left on the local network where it can be poisoned. The mode looked enabled and did nothing. Supporting evidence that the behaviour existed before: the settings migration still reads the old booleans `enable_final_resolve_by_proxy` / `enable_proxy_resolve_by_proxy` (`setting_manager.dart:794-801`) and folds them into `proxyResolveMode = proxy`. There is no git history to trace it — commit `227f5f1` is the squashed upstream import (every file added at once).

**Fix** (3 edits in `lib/app/utils/singbox_config_builder.dart`):
1. `_dnsServerFromUrl(..., {String? detour})` now emits `out['detour']`.
2. `dns()` computes `remoteDetour = (resolveMode == proxy && !setting.tls.enableServerless) ? kOutboundTagProxy : null` and passes it for the `dns-remote-*` servers only. Serverless is excluded because its selector has no real node to dial.
3. `route()`'s `default_domain_resolver` used to be hardcoded to `dns['servers'].first`; it now picks the first server **without** a detour, so resolving a node whose address is a domain can never need the proxy that is still being built. In the non-proxy modes nothing is detoured, so the first entry still wins exactly as before.

**Verified the core honours it**: every DNS transport calls `dialer.InitializeDetour` (`dns/transport/{udp,tcp,tls,https,quic}.go`), and `DialerOptions.Detour` (`option/outbound.go:68`) is embedded in the remote DNS server options.

**Tests**: `test/dns_resolve_mode_test.dart` — proxy mode detours the remote resolvers; fakeip/direct/serverless leave them direct; `default_domain_resolver` is never detoured. First run 4/5 passed and the failure was my own test bug (I passed `null` for `route()`'s `dns` argument), now fixed.

Note: the `dns-resolver-N` servers built from `getResolverDns()` are still emitted but referenced by no route rule — dead config. Flagged, not changed.

## Tooling note

Long foreground commands are killed with **SIGTERM** in this session (seen on `flutter clean`, `pub get`, the cache copy, and a test run). Anything expected to take more than ~30 s must use `run_in_background=true` and be polled via `TaskOutput`.

**But `run_in_background` does NOT get the sandbox bypass**, and `flutter build windows` needs it (the sandbox blocks `vswhere`, giving a misleading "Unable to find suitable Visual Studio toolchain"). So Windows builds must run in the **foreground** with `dangerouslyDisableSandbox: true` — which is fine because they finish in ~60–160 s, under the SIGTERM threshold.

## I damaged `pubspec.lock` with the mirror work — repaired

Reviewing the diff caught a side effect of my own doing: `flutter pub get --offline` had **stripped 172 `sha256` content hashes** from `pubspec.lock` (the URLs stayed `https://pub.dev`, so there was no mirror pollution — just the hashes gone). Those hashes are a supply-chain check: they detect a package silently changing under the same version. A 172-line deletion in a tracked file is also exactly the kind of noise that ruins a commit.

**Why it happened:** pub records a package's archive hash in `<cache>/hosted-hashes/<host>/<pkg>-<ver>.sha256`. The cache had been pruned and I rebuilt it by hand-copying directories and extracting tarballs myself, so no hash files existed for those 172 packages. Unable to produce a hash, pub wrote the lockfile entries without one.

**Fix — write the hashes back from the lockfile itself** (the lockfile is the source of truth and still had them in git):
1. `git checkout pubspec.lock` to restore the original.
2. For every `source: hosted` entry, write `hosted-hashes/pub.dev/<name>-<version>.sha256` containing its hash.
3. Re-run `pub get --offline` and confirm the lockfile is untouched.

**Gotcha that cost a round trip:** the lockfile mixes formats — most entries are `sha256: "abc…"` (quoted) but some are `sha256: abc…` (bare). A regex requiring quotes silently skipped 64 of them, and the second pass still stripped exactly those 64. Use `sha256:\s*\"?([0-9a-f]{64})\"?`.

Verified end state: `git diff pubspec.lock` is **empty**, 272 hashes intact, cache now holds 550 hash files.

**Lesson:** before running `pub get` against a hand-rebuilt cache, or before finishing any task that touched the pub cache, run `git diff --stat` and check for lockfile churn. Never leave a lockfile with its content hashes removed.

## Restored the three per-purpose DNS switches (2026-09-17)

User: *"still not thoose settings"* — i.e. add them. Implemented, since the original semantics are unrecoverable (see the entry above) but the *labels* and the migration keys pin down what each flag is for.

**Design — additive, never contradictory.** `proxyResolveMode` (the Resolve Channel dropdown) and the three flags can each turn a behaviour **on**; neither can turn one off:
```dart
final fakeIp = resolveMode == fakeip || dns.enableFakeIp;
final resolveByProxy = resolveMode == proxy || dns.enableProxyResolveByProxy;
```
So a user on the dropdown keeps working exactly as before, and the switches are real rather than decorative.

**Changes:**
- `setting_manager.dart` — three bools on `SettingConfigItemDNS`, serialised under the **same legacy keys the migration already reads** (`enable_fake_ip`, `enable_proxy_resolve_by_proxy`, `enable_final_resolve_by_proxy`) so old configs round-trip. On load, if the config carries only `proxy_resolve_mode` the flags are **derived from it**, so the switches and the dropdown never disagree on first load.
- `group_helper.dart` — three switches in `showDns`'s `options4`, inside the existing `if (!novice)` block, above Resolve Channel.
- `singbox_config_builder.dart` — `fakeIp` / `resolveByProxy` replace the raw mode comparisons; `enableFinalResolveByProxy` additionally forces `remoteDetour` on and, in `direct` mode, points `dns.final` at a detoured server (otherwise "final through the proxy" would have nothing to point at).
- 6 i18n keys (label + tips ×3), en + fa, synced to 28 locales.

**Test trap worth remembering:** `route['final']` is the fallback **outbound**, not a resolver — `dns['final']` is the resolver. My first assertion compared them and failed with `Actual: proxy`; the code was right, the test was wrong. 4 new tests (each switch working alone with the dropdown on `direct`, plus a guard that everything-off detours nothing). **45 tests pass**, analyze clean.

Build verified: markers `dnsEnableFakeIp` / `dnsEnableProxyResolveByProxy` / `dnsEnableFinalResolveByProxy` (×4 each) in `data/app.so`; zip rebuilt (2942 files, 41.7 MB, integrity OK); and the user's **extracted** copy at `dist/karing_1.2.24_windows_x64/` was refreshed in place so their existing launch path picks up the change.

## Caught a bug in my own restored toggles before shipping it (2026-09-17)

Following up on the additive-switch design, I checked who else writes `proxyResolveMode` — because the switches are **additive**, a flag left on would keep forcing its behaviour no matter what the dropdown said.

Found it: the Resolve Channel `onPicker` is the **only** writer (verified by grepping every `proxyResolveMode =` in `lib/`; `dns_auto_setup_screen.dart` only *reads* it). Combined with deriving the flags from the mode on load, that produced a real defect: a user on `proxy` loads with both proxy flags **true**, then picks `direct` — the dropdown flips but the flags stay on, so `resolveByProxy` remains true and **DNS still detours**. The dropdown would have looked broken, in exactly the scenario the user was about to test.

**Fix:** extracted the sync into `SettingConfigItemDNS.syncResolveFlagsToMode()` and call it (a) from the picker, so the dropdown stays the master control, and (b) from `fromJson` when the config carries no legacy flags. Pulling it out of the UI closure also made it testable — 5 new tests cover direct/proxy/fakeip sync, a mode-only config deriving the switches, and a legacy config keeping its flags verbatim.

**Lesson:** when adding a second control over state that already has one, grep for *every* writer of that state before shipping. The additive design was fine; the missing piece was that the pre-existing writer had to know about it. 50 tests pass.
