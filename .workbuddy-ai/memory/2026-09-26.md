# 2026-09-26

## Android: TUN would not enable — a Windows-only port probe was running everywhere

User report: *"the tun alert we added had a problem in Android, make it just for Windows; in Android
the TUN is not enabling."*

### The alert was innocent

`getTunMode` in `vpn_service.dart:196` and the Settings switch in `group_helper.dart:348` were **both
already guarded** with `Platform.isWindows`. The suspicion was wrong.

### The real cause was its sibling

`SettingManager.ensureCorePortsAvailable()` — added in the same batch of work — had **no platform
guard at all**. It binds each configured port to test it and, on failure, **shifts the port and saves
the new value**.

On Android that is actively harmful: the **running core already holds those ports**, so every start
fails to claim them, shifts them, and persists the result. The core then comes up on ports the rest of
the start-up path does not expect, and **TUN never comes up**.

The function's own doc comment says the problem it solves is Windows-specific — *"a port can sit inside
a WinNAT/Hyper-V reserved block and Windows refuses it outright"* — which is exactly the guard that was
missing.

### Fix

```dart
static Future<void> ensureCorePortsAvailable() async {
  // Windows only. ...
  if (!Platform.isWindows) {
    return;
  }
```

### Lesson

**Guard platform-specific work where it runs, not only where it is called from.** I added a
Windows-only *feature* and a Windows-only *port probe* in one change; only the first got its guard. The
second then quietly corrupted state on Android — worse than failing, because it **saved** the damage.

**Residual risk:** ports already shifted on the device stay shifted. If TUN still misbehaves after this
build, the saved ports are the first thing to check and reset.

Verification: `flutter analyze lib/` 0 errors; full suite passes (156 + the known load-harness flake,
which passed on retry).
