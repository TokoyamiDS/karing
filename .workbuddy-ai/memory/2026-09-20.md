## Cloudflare configs: the app discarded each node's own TLS fragmentation

User: *"the app does not have good treatment with cloudflare configs, like so much of them not
even testing latency"*. Vague, so I measured the profile before touching code.

### The measurement (`subscriptions.json`, not the dead twin)

75 servers across 9 groups. **57 flagged Cloudflare. All 57 had no latency. 5 of 75 had any
latency at all.** The problem was concentrated: the **`patterniha` group — 50 servers, all 50
CF, 0 with latency** (subscription `patterniha/Free-Configs`).

Their stored latency was the literal string **`"An error occurred in the delay test"`** — so the
test *ran* and failed; it was not being skipped. That string is **not in the app's i18n or Dart**
— it is the **core's** Clash API error body, which proved the test went through the core.

**`karing_subscribe.json` is the dead twin of `subscriptions.json`** (same trap as
`karing_setting.json` / `setting.json`). The dead one has no `raw` and no latencies; reading it
first gave a confidently wrong "0 CF nodes, 0 latencies".

### Reproduced, then isolated

1. Probed the config by hand: TCP to `188.114.97.6:443` = 21 ms, TLS OK, and a WebSocket upgrade
   to the worker path returned **`101 Switching Protocols`**. **The transport is alive.**
2. Extracted that exact built outbound from `core_config.json` into a minimal config (mixed
   inbound + `clash_api`, no TUN) and ran the bundled core:
   - `https://www.gstatic.com/generate_204` → **504 Timeout**
   - `http://cp.cloudflare.com/generate_204` → **503 `{"message":"An error occurred in the delay
     test"}`** — the exact stored string.
3. Removing the fragment settings changed 503 → 504 but still failed, so fragmentation was not
   the whole story: **that particular worker is simply dead** (CF answers the upgrade, the tunnel
   carries nothing — normal for a stale public config).

### The actual defect

`auto_conf_utils._tlsFromParams` (the clash-side share parser) **does** read the provider's own
`fm=` finalmask and prefers it:

```dart
tls['fragment_sizes'] = fmSizes.isNotEmpty ? fmSizes : tlsSetting.fragmentSize...;
```

But the **sing-box config builder has its own parser, `_tlsFromUrlParams`, which never parsed
`fm=` at all** — `fm` appeared nowhere in `singbox_config_builder.dart`. So a node lost the
fragment lengths its own publisher tuned, and then two places **overwrote** what was left:

- `_tlsFromUrlParams`: `if (isIr) { tls.fragmentSizes = kFragmentSizesPatt; tls.cipherSuites =
  kCipherSuitesPatt...; }` — unconditional.
- `_applyPattFragment`: the same, for **every** TLS outbound, whenever `iranMode` is on.

Evidence in the built outbound: the source link carried `fm=` with `lengths: ["0","104","1"]`;
the emitted outbound had `fragment_sizes: ["5","94","1","109","1"]` (Patt's preset) and **no
`finalmask` at all**. 50 nodes handed one identical preset.

**The "treatment" was: read the provider's tuning, throw it away, substitute Patt's.**

### The fix

1. **Parse `fm=` in `_tlsFromUrlParams`**, mirroring `auto_conf_utils` (which already works).
2. **Make Patt's preset a fallback, not an override** — `if (tls.fragmentSizes.isEmpty)` in the
   `isIr` branch, and `??=` throughout `_applyPattFragment`.

Fragmentation itself is still forced on in Iran (`enableFragment || isIr`) — that is the
deliberate DPI hardening and I left it alone. Only the provider's *values* are now preserved.

### Verification

- New `test/cloudflare_fragment_preserve_test.dart` (4 tests): the config's `fm=` lengths and
  cipher list survive Iran mode; the preset still fills a node that ships no tuning; outside Iran
  nothing is injected.
- `sing-box check` on a config carrying the **provider's** fragment values → silent, exit 0.
- **91 tests pass, 0 failures** across 14 files.

### Two traps worth remembering

- **`dns_direct_probe_test.dart` and the network probes flake as `did not complete`.** That is
  the host transport flake, not a failure — it passed on retry, and once showed `+6 ~3` (3

# Inline exit location in the profiles list (flag + IP, in front of the ping)

## The data gap, which is the whole story

**The app had no per-node country anywhere.** `ProxyConfig.outletregion` is *declared and
serialised into `raw['outlet_region']` but never assigned* — the same
declared-but-never-wired pattern as `mixedDirectNetSharePortDefault` and the statistics stub.
There is **no offline GeoIP database** (only `ir.srs` under `ruleset/geoip`), and
`outletip` was only filled when `latencyCheckResoveIP` was on — which is **off** for this user,
so all 75 nodes had `outlet_ip: ""`.

So the flag needed a source, and I asked rather than guessed (a wrong guess costs a build cycle
this user cannot currently run). The answers:

- **Which IP → the exit IP**, with the reason *"because there can be cloudflare fake ips"*.
  Correct and worth keeping: 52 of their nodes dial `188.114.97.6`, a Cloudflare anycast address
  whose geolocation says nothing about where traffic comes out. The configured address is
  useless for this.
- **Flag source → "do what v2rayn does"**, i.e. automatic. v2rayN ships a GeoIP DB; this app has
  none, so the closest achievable is a geoip lookup **through the node** — the app already does
  exactly that for the home screen card via `api.ip.sb/geoip`.

## The change

1. **`server_manager.dart`** — the latency-test success branch now fetches
   `https://api.ip.sb/geoip` (was `checkip.amazonaws.com`, which returns a bare IP and therefore
   cannot give a flag), parses `ip` + `country_code`, and stores both. If the body is not JSON it
   falls back to treating it as a bare address, so only the flag is lost.
2. **Resolve-once semantics.** The old gate was `latencyCheckResoveIP`, whose own label is
   *"When manually checking, resolve the outlet IP"* — manual only, so it could never be
   automatic. Now: `latencyCheckResoveIP || config.outletip.isEmpty`. Manual checks still
   re-resolve (unchanged); any successful test fills the location in **once** if unknown, then
   skips. Cached on the node, so it costs one request per node ever, not one per cycle.
3. **`proxy_conf_utils.dart`** — added `outletregion` to `toJson`/`fromJson`. It was only being
   written into `raw['outlet_region']` by `updateByDelay`, and `fromJson` never read it back, so
   the flag would have vanished on the next app start.
4. **`my_profiles_screen.dart`** — renders `"${flag} ${ip}".trim()` immediately before
   `CommonWidget.createLatencyWidget`, wrapped in `Flexible` with `maxLines: 1` + ellipsis so it
   cannot overflow the row. `EmojiUtils.countryCodeToEmoji("")` returns `""` (length != 2), so a
   node with no country shows just the IP and one with neither shows nothing.

**No new i18n keys** — the label is a flag and an IP.

## THE ROOT CAUSE — Windows TLS-fragment wait-for-ack is fatal here

The logging immediately paid for itself. With the core at `debug`, a 60-second run gave
**56 successes and 49 failures, 89% of the failures this**:

```

```

Chain: Iran mode forces `tls.fragment = true` on every TLS outbound → `tf.Conn.Write` splits the
ClientHello and calls `writeAndWaitAck` per fragment → `winiphlpapi.WriteAndWaitAck` enables

**`ERROR_NOT_SUPPORTED`** → `common/tlsfragment/wait_windows.go` only caught
**`ERROR_ACCESS_DENIED`**, so the error was **fatal** → the connection died → the delay test
reported the generic `503 {"message":"An error occurred in the delay test"}`.

**Controlled proof** (same config, only fragmentation toggled): frag ON → **49 EStats errors, 0
core checks passing**; frag OFF → **0 EStats errors, 21 passing**.

**Fix applied** to `D:\Flutter Projects\sing-box\common\tlsfragment\wait_windows.go` (branch
`dev-next`): treat `ERROR_NOT_SUPPORTED` like `ERROR_ACCESS_DENIED` and fall back to the plain
write + `fallbackDelay` pacing. Safe because both errors surface from *enabling* the collection,
before `conn.Write`, so re-writing is not a duplicate. **The core is a prebuilt binary
(`windows/sing-box.exe`, Sep 5) — it must be rebuilt with Go and copied over.**

# Fragment-walk panic in c394e59 is real — but the Go TOOLCHAIN decides whether it fires

**Correction of an earlier wrong claim in this file.** I first concluded "the shipped core revision
panics, the shipped binary is crashing". **That was wrong**, and the correction is the more useful
finding.

## What is true at the source level

`git diff c394e59 a7eb0a7 -- common/tlsfragment/conn.go` shows a genuine bug. The old code builds a
monotonic `splitIndexes` and *then* patches the first element after the fact:

```go
if c.splitRecord && len(splitIndexes) > 0 && splitIndexes[0] <= recordLayerHeaderLen {
    splitIndexes[0] = recordLayerHeaderLen + 1   // = 6
}
```

If the second index is also < 6 the array becomes non-monotonic (`[6, 2, ...]`) and
`payload[splitIndexes[i-1]:splitIndexes[i]]` panics with `slice bounds out of range [6:2]` at
`conn.go:174`. `a7eb0a7` fixes it by flooring the first index *during* the walk. Reachable because
`fragment_sizes` starts small on **all 55** fragmented outbounds (`["0","104","1"]` ×49, Patt
`["5","94","1","109","1"]` ×6).

## What is NOT true: the shipped binary was never crashing

Same config, same `-D`, same reported `Revision: c394e59`, same 6 tags — only the build differs:

| build | Go | panics |
|---|---|---|
| **the user's shipped binary** | 1.24.7 | **0 / 8** |
| a clean rebuild of `c394e59` | 1.26.1 | **7 / 7** |
| `a7eb0a7` + the ESTATS fix (installed) | 1.26.1 | **0 / 8** |

So the panic is **toolchain-dependent**. A clean `c394e59` build with Go 1.26.1 panics every time;
the shipped `c394e59` binary built with Go 1.24.7 never does. `math/rand` seeding and `crypto/tls`
ClientHello construction both changed across those releases, either of which changes the walk's
inputs.

**The methodological lesson is the valuable part:** when two builds of the "same revision" behave
differently, suspect the compiler before the code. I ran the rebuild alone and believed it. Only
running *both* under one identical invocation exposed the toolchain as the variable. **Compare like
for like — same config, same `-D`, same command line, and read the Go version out of `version`.**

Also note: `log.level: debug` + `log.output` vs the app's `warn` looked like the variable for a while
(6/6 vs 0/8) and was a red herring — with exit-code measurement both were 0/5. **Small samples lied
twice here.** Classify with the exit code (124 = survived, 2 = panic), not with grep on output.

## Consequence: `a7eb0a7` is still the right revision

Not because the shipped binary was crashing, but because the bug is real at the source level and you
cannot control which toolchain ships next. Prefer the revision that is correct in the code.

## Two build details worth keeping

- **`Revision:` comes from Go's module pseudo-version, not VCS stamping.** Building in a
  `git worktree` yields `(devel)` and the `version` output has **no Revision line at all** — which

# Where the statistics feature lives in the UI (asked 18:58)

The traffic-statistics feature is reached by **Home → the "Statistics and Analysis" card → the
group's own rows**. The card is `StatisticsAndAnalysisCard`, `id() == "statistics"`
(`home_screen_widgets.dart:1420`), label `meta.statisticsAndAnalysis`, and `home_screen.dart:428`
binds `onTapStatistics` → `GroupHelper.showStatistics(context, "home")`.

That group (`group_helper.dart:995`) holds **Enable**, data-desensitize, cache days, cache limit,
and a **Records** row that pushes `StatisticsRecordsScreen` (`group_helper.dart:1078`).

**`statistics.enable` defaults to `false`, and `StatisticsRecorder.pollOnce` returns early when it is
off** (`statistics_recorder.dart:60`) — so the screen shows the `enableHint` text and no data until
the switch is flipped. Easy to mistake for a broken feature; mention the switch first.

Recording only runs **while connected** (`_startStatistics()`/`_stopStatistics()` in
`home_screen.dart:706`), polling the core's `/connections` every 2 s and storing deltas in
`datas/statistics.db`, which is why the report survives stopping the VPN. The user's home widget
list already contains `"statistics"`, so the card is on their home screen already.

# Why AI traffic drops and reports "retry" — and the one-line fix

User: *"i do work so much with ai and upstream results, but sometimes its has problem and says about
retry, is there a way to make it more stable for ai?"* They chose **keep live connections across a
node switch** and nothing else.

## The mechanism

`route.final = proxy`, and `proxy` is a **selector** whose `default` is a single node — in their case
a Cloudflare Worker (`👉🆔@v2ray_configs_pool📡🇺🇸®️U`, 188.114.97.6), the least durable kind, and 49
of their 60 nodes are dead CF Workers. AI assistants answer over **long-lived streaming
connections**, so anything that tears connections down mid-answer surfaces as "retry".

**`interrupt_exist_connections: true` was hardcoded in all four group constructions**
(`singbox_config_builder.dart` 215/228/1003/1010) — not a setting. Every switch therefore dropped
every live connection. Changed all four to **`false`**: a switch now only affects connections opened
afterwards. Cost: connections to a node that has since died linger until they time out instead of
being cut immediately.

Verified: new assertion in `test/selector_default_test.dart` (**7 tests pass**, exit 0 first try),
`flutter analyze` 0 errors, and `sing-box check` on their real config with the field flipped →
**exit 0**, so the core accepts it.

## Two adjacent findings — do NOT assume these settings work

1. **The whole "Auto Select" settings group is cosmetic.** `autoSelect.*` is referenced **only** in
   `settings_screen.dart` (UI) and `setting_manager.dart` (model) — never by the config builder or
   server manager. `interval`, `tolerance`, `reTestIfNetworkUpdate`,
   `updateCurrentServerAfterManualUrltest`, `prioritizeMyFav`, `filter` all do nothing. Their stored
   `interval: 28800` has no effect.
2. **`selectedHealthCheckInterval` is the notable one.** The settings row reads *"Current server
   health check interval"* with the tooltip *"If the check fails, the server is switched; if no
   available server is found when switching the server, the group will re-check latency"* — exactly
   the feature that would fix a dead selected node. It is **displayed but never wired**, and there is
   no auto-switch-on-failure logic in `server_manager.dart` either. I offered to implement it; the
   user did not take it up this round.

Also worth knowing: the `AutoSelect` urltest is emitted with **no `interval`**, so the core uses its
own default re-test cadence with `tolerance: 50`. With interrupting now off, that churn is harmless —
it only changes where *new* connections go.

**Unchanged on purpose:** `mux` is already off (good — multiplexing breaks streaming), and TUN is off
(`tun.enable: false`), so only proxy-aware apps are tunneled. That is a separate trade-off, not
touched.
