# 2026-09-25

## Android build failed — JVM could not reserve its heap (not a code error)

`flutter build apk --release` failed in ~19s with:

```
e: Failed connecting to the daemon in 4 retries
e: Daemon compilation failed: Could not connect to Kotlin compile daemon
Execution failed for task ':gradle:compileKotlin'
```

The real line, further down the log:

```
exception: openJDK 64-Bit Server VM warning: os::commit_memory(0x0000000684000000, 398458880, 0)
failed; error='The paging file is too small for this operation to complete' (DOS error/errno=1455)
```

And `android/hs_err_pid*.log` said it plainly — those dumps were timestamped to match my attempts:

```
# There is insufficient memory for the Java Runtime Environment to continue.
# Native memory allocation (mmap) failed to map 398458880 bytes. Error detail: G1 virtual space
```

**Cause:** the machine had **2.6 GB of commit free out of 35.4 GB**, while the build wanted ~3.5 GB —
Gradle at `-Xmx2048M` **plus a separate out-of-process Kotlin daemon at `-Xmx1536M`**.

## The non-obvious part: `android/gradle.properties` does NOT reach `:gradle`

```
android/settings.gradle.kts:10:  includeBuild("$flutterSdkPath/packages/flutter_tools/gradle")
```

`:gradle` is **Flutter's own Gradle plugin, pulled in as a composite build**. A composite build does
not read the app's `gradle.properties`, so my first fix — switching
`kotlin.compiler.execution.strategy=in-process` in `android/gradle.properties` — **had no effect at
all**: the stack trace still showed `compileWithDaemon`.

**The fix belongs in `~/.gradle/gradle.properties`**, which applies to every build including included
ones:

```
org.gradle.jvmargs=-Xmx1024M -XX:MaxMetaspaceSize=512M -XX:ReservedCodeCacheSize=128M -Dfile.encoding=UTF-8
kotlin.compiler.execution.strategy=in-process
```

One JVM instead of two: ~1.5 GB of commit instead of ~3.5 GB.

**Verified:** after the change the next attempt logged `kotlin-daemon failures: 0` and ran to normal
javac warnings before a machine reboot interrupted it. That is the fix confirmed.

## Files touched

- `~/.gradle/gradle.properties` — **created** (none existed). This is user-global and affects *all*
  Gradle builds on the machine, not just this project. Conservative heaps, so it is safe, but slower.
- `android/gradle.properties` — `out-of-process` → `in-process`. Backup `gradle.properties.bak-oom`.
  Redundant given the user-level file, but correct on its own and harmless.

## Standing note

This machine runs a heavy multi-agent stack and sits close to its commit limit. **Android builds need
~1.5–3.5 GB of commit.** When a build dies with `Could not connect to Kotlin compile daemon`, check
`android/hs_err_pid*.log` first — it is almost always memory, never the Kotlin code.

## ⚠️ `flutter clean` is NOT safe on this machine

After the Kotlin fix, packaging failed at `:app:packageRelease` →
`PackageAndroidArtifact$IncrementalSplitterRunnable`, with **no cause in the log**. I judged that a
half-written incremental state from the crashed build, and ran `flutter clean`.

**That was a mistake.** `flutter clean` deletes `.dart_tool`, which forces a `pub get` — and
**`pub.dev` returns 403 from this network**:

```
Authentication error (403)
  package:pub/src/authentication/client.dart 90  _AuthenticatedClient._throwAuthException
Failed to update packages.

curl https://pub.dev        -> 403
curl https://pub.dartlang.org -> 403
```

The dependencies had been resolved long ago, so nothing needed the network until I removed them.

**Recovery: `flutter pub get --offline`.** The pub cache (~2 GB) still had everything and it reported
`Got dependencies!`, restoring `.dart_tool/package_config.json`. There is also a
`pub.flutter-io.cn` mirror in the cache, which is the fallback if the cache is ever incomplete.

**Rule: on this machine, never `flutter clean` to fix a build.** Delete the Android intermediates
instead (`build/app`, `android/app/build`) and leave `.dart_tool` alone — or run
`flutter pub get --offline` first so the deps survive.

## ✅ Resolved — the memory sizing that actually works

Three failures, each a different memory symptom. The final working values:

```
org.gradle.jvmargs=-Xmx3072M -XX:MaxMetaspaceSize=1024M -XX:ReservedCodeCacheSize=256M -Dfile.encoding=UTF-8
kotlin.compiler.execution.strategy=in-process
```

| attempt | settings | failure |
|---|---|---|
| 1 | Gradle 2 GB + **out-of-process** Kotlin 1.5 GB | `Could not connect to Kotlin compile daemon` (commit exhausted) |
| 2 | `-Xmx1024M`, **`MaxMetaspaceSize=512M`**, in-process | **`OutOfMemoryError: Metaspace`** on `:vpn_service:compileReleaseKotlin` |
| 3 | `-Xmx3072M`, `MaxMetaspaceSize=1024M`, in-process | **SUCCESS** |

**The lesson:** in-process Kotlin needs a *generous* metaspace — it loads far more classes than a
512M budget allows. Reducing the heap was right; reducing metaspace at the same time was wrong. The
error even said so: *"Not enough memory to run compilation. Try to increase it via 'gradle.properties'"*.

Machine had 7.4 GB RAM / 10.9 GB commit free at the time, so 3 GB + 1 GB was comfortable.

Plus the per-ABI splits (41.9 MB, 42.6 MB). **Verified signed** — my first check looked for

META-INF. `apksigner verify` confirms:

```
Signer #1 certificate DN: CN=karing, OU=personal, O=personal, L=local, ST=local, C=IR
```

**Note for next time:** check the signing block (`APK Sig Block 42`, v2 id `0x7109871a`), not META-INF.
