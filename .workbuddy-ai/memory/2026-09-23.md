# 2026-09-23

## "Sometimes it crashes the WiFi and I must wait for the driver to restart"

User report. Investigated via Windows event logs rather than guessing. **The WiFi is not crashing —
Windows is deliberately restarting it**, and the trigger is environmental.

### What the reports actually show

| evidence | reading |
|---|---|
| `WLAN-AutoConfig` id **4003** × **134** in 30 days | "detected limited connectivity, attempting automatic recovery" |
| followed by id **4001** (service stopped) → **4000** (service started) | the WLAN service and the `mtkihvx.dll` extensibility module are **restarted** — a ~1–2 min outage, exactly the wait described. e.g. 05:49:19 → 05:51:06 = **1m47s** |
| `Tcpip` warning × 3 | **"A request to allocate an ephemeral port number … has failed due to all such ports being in use"** |
| `Tcpip` warning × many | "selected local endpoint was recently used to connect to the same remote endpoint" |
| adapter | **MediaTek Wi-Fi 6 MT7921**, driver `25.40.2.586` (2026-01-30) |
| SSID | **`TokoyamiDS_Phone`** — a **phone hotspot**, 802.11n ch.11, 72.2 Mbps, signal 87% |
| `Get-NetAdapter` | **`xray_tun` (Wintun) Up**, alongside Wi-Fi; VMware VMnet1/8 and two Hyper-V vEthernet adapters also Up |
| default routes | **three** `0.0.0.0/0`: `xray_tun` metric **0**, Wi-Fi metric 55, Ethernet Default |
| processes | **`v2rayN` pid 23380 + `xray` pid 5216 running while Karing runs** |
| startup | `v2rayNAutoRun…` → **v2rayN auto-starts at login** |
| TCP tuning | **`MaxUserPort = 15000`** (non-standard; matches the dynamic range 1024–15000), `TcpTimedWaitDelay` unset = **120 s** |

### Diagnosis

1. **Two VPN clients run at once.** v2rayN/xray installs a Wintun adapter with a **metric-0 default
   route** competing with Karing's TUN and the Wi-Fi gateway. Both manipulate routes and DNS.
2. **The "WiFi" is a phone hotspot**, which drops routinely.
3. Windows reacts to the resulting **"limited connectivity"** by **resetting the WLAN adapter**
   (4003 → 4001 → 4000). That reset *is* the symptom the user experiences.
4. Separately, the **ephemeral pool is capped at ~14,000 ports** (`MaxUserPort=15000`, TIME_WAIT 120 s)
   and the machine genuinely exhausted it — heavy churn from two VPNs, 30 latency workers, CF-IP
   rotation and many concurrent AI agents.

### A hypothesis I killed

My first theory was NCSI: the tunnel swallowing `www.msftconnecttest.com` so Windows decides there is
no internet. **Refuted by reading the registry** — `EnableActiveProbing = 0`, so active probing is off.
Worth recording because it *sounds* right and would have shipped a fix for the wrong cause.

### Also confirmed

The user **rebuilt and is running the new build** — `_windowsStartCore: ready on 15404`, i.e. the new
port block is live.

And the app restarts the **entire core** on every node/config change: `gen=7,8,9` within seconds,
driven by CF edge-IP rotation for the same tag. That is avoidable churn and the one part of this that
is ours to fix.

### Plan given (ordered by impact, not by effort)

1. Stop v2rayN auto-starting; never run two VPN clients together. **Zero code, biggest effect.**
2. Phone hotspot: keep the phone awake/plugged in, battery saver off, prefer 5 GHz.
3. Restore the port pool: `netsh int ipv4 set dynamicport tcp start=49152 num=16384` and
   `TcpTimedWaitDelay = 30` (both need a reboot). 15400+ stays outside either range.
4. **Code:** stop rebuilding the core for a same-tag address change.
5. Enable the WLAN operational log to confirm the correlation next time.

## ✅ IMPLEMENTED: refuse to add a second tunnel, and say why

User: *"lets make the karing to show a popup and say this and dont turn on its tun until we disable
the v2rayn tun"*.

**Detection** — `NetworkUtils` (`network_utils.dart`):

- `_foreignTunnelHints` — adapter-name fragments (`tun`, `tap`, `wintun`, `wireguard`, `openvpn`,
  `nebula`, `zerotier`, `tailscale`, `radmin`, `sing-box`, `clash`, `v2ray`, `xray`, `hiddify`,
  `nekoray`, `proton`). Deliberately specific so `Ethernet`, `vEthernet` and VMware do not match.
- `kOwnTunnelInterface = "karing"` — matches `SingboxInboundTunOptions.interfaceName`, so our own
  tunnel is never mistaken for a foreign one.
- `isForeignTunnelName(name)` — the pure predicate, **extracted so it can be tested**: a false
  positive silently downgrades a working setup to proxy mode.
- `findForeignTunnels()` / `hasForeignTunnel()` — via `NetworkInterface.list()`, which reports the
  adapter **name** on Windows (verified: `xray_tun` appears). Only *up* adapters are listed, so a
  disconnected competitor is correctly ignored.

**Gate** — `VPNService.getTunMode()` returns **false** when a foreign tunnel is present (Windows
only), so the core never fights for the default route. The VPN still works through the system proxy.

**Popup** — `home_screen.dart`, in the start path after the error check: logs the conflict and shows
`t.HomeScreen.foreignTunnel(adapters: …)`.

**i18n** — new key `HomeScreen.foreignTunnel` in **all 28 locales** (real English + Persian, English
fallback elsewhere), then `dart run slang`. Parity test passes.

### Trap that cost a pass — and a skill fix

My first insertion anchored on the neighbouring key `corePortReserved` and matched **2 of 28**
locales. **Key order differs per locale**: that key is mid-block in `en`/`fa` (trailing comma) but the
**last** key everywhere else (no comma), so the pattern requiring `,` could not match.
**Anchor on the namespace opening instead** — order-independent, always matches.
`karing-i18n-key-addition` has been corrected: its old example pattern only worked for a
single-key namespace.

  and `VMware … VMnet1`) left alone.

## ✅ Follow-up: a Bypass, because the detection can be wrong

User: *"also add skip or bypass button, its sometimes not validating right"*.

**The ordering constraint is the whole subtlety.** The check must run **before `setServer()`** — the
`tun-in` inbound is baked into the config inside `setServer`, so bypassing *after* it would set the
flag but never add the inbound back, and the user would need a second attempt. My first version put
the dialog after `setServer` and had to be moved.

What was added:

- **`showConfirmDialog` gained optional `okText` / `cancelText`** — parameterised rather than
  duplicating ~50 lines of dialog code for one custom button.
- **`SettingConfigItemTUN.ignoreForeignTunnel`** (persisted, `ignore_foreign_tunnel`). A bypass that
  did not persist would nag on every launch — covered by a round-trip test.
- **`getTunMode()`** skips the check when the override is set.
- **`HomeScreen._checkForeignTunnel(disableShowAlertDialog)`** — one shared helper, because there are
  **two start paths** in `home_screen.dart` (`setServerAndReload` and `checkAndReload`), both of which
  build a config. A one-shot `_foreignTunnelPrompted` guard stops the dialog appearing twice.
- **Bypass** sets the override, saves, and logs. The start then proceeds **with TUN**.
- **Settings → TUN → "Warn about other VPN tunnels"** (Windows only, inside the `!novice` block) —
  the way back, and the way to silence it permanently if the detection is consistently wrong.
- i18n: `HomeScreen.foreignTunnelBypass`, `SettingsScreen.foreignTunnelCheck`,
  `SettingsScreen.foreignTunnelCheckTips` — all 28 locales, then `dart run slang`.

### Verification

- `test/foreign_tunnel_detection_test.dart` — **5 tests pass**, now including the override's
  save/load round-trip and its off-by-default state.
- `test/i18n_locale_parity_test.dart` — **passes**.
- Full suite — **140/140, exit 0**, fully green this run.
- `flutter analyze` — 0 errors. The `network_utils.dart` change is purely additive (+68 lines), so the
  pre-existing unused-import warnings there are not ours.
