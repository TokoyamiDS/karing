# Downloads were being killed by the request deadline — the real "retry"

The user clarified: *"i want the karing to be more efficient while upstreaming or downloading. Like
sometimes i just can download 10mb but its cancels because of failed upstream."* **"Upstream" is
their paraphrase — it is not a literal string** in the app, the i18n, or the core.

## The bug

`HttpUtils.httpDownload` raced the **entire transfer, body included**, against the per-request
deadline:

```dart
HttpClientResponse? response = await Future.any([
  waitResponseDone(request, path),        // resolves only after response.pipe(...) finishes
  waitResponseTimeout(request, timeout),  // 60 s default
]);
if (response == null) { return error("http response timeout after ${timeout.inSeconds} seconds"); }
```

`waitResponseDone` awaits `response.pipe(File(path).openWrite())`, so it completes only when the
**whole body** has been written. Any download outliving the deadline was aborted — and
`DownloadUtils.downloadWithPort` then **deletes the `.tmp`**, so no progress was ever kept.

**10 MB in 60 s ≈ 1.4 Mbit/s** — entirely normal on an Iran→upstream route, which is why it always
died at roughly the same size. The retry loop in `DownloadUtils.download` only iterates *ports*, not
attempts, so a slow link could never finish anything large.

## The fix

`timeout` now bounds only how long the **server may take to answer**; the transfer is guarded against
**stalling** instead:

```dart
HttpClientResponse response = await request.close().timeout(timeout);
...
final sink = File(path).openWrite();
try { await response.timeout(kDownloadStallTimeout).pipe(sink); }
catch (err) { try { await sink.close(); } catch (_) {} rethrow; }
```

`kDownloadStallTimeout` = 30 s of *zero bytes* (`http_utils.dart`). As long as bytes keep arriving a
download may take as long as it needs; a silent upstream is still abandoned, so nothing hangs.

**Scope is tight and deliberate:** only `httpDownload` needed this. The other four `Future.any` call
sites (`httpHeadRequest`, `httpGetRequest`, the post variants) pass `path: null`, so they return
after the headers and the race is correctly scoped for them. `httpUpload` has **no timeout at all**,
so uploads were never affected. `group_helper.dart:2797`'s hardcoded **10 s** backup-zip deadline is
now header-only, which is a defensible meaning for it.

## Verification

`test/http_download_stall_test.dart` drives the real function against a local `HttpServer`:

1. **4 MB delivered over ~4 s with a 1 s deadline → succeeds** (under the old code this could only
   fail). Asserts the full body lands on disk.
2. **Headers then silence → still fails**, so the stall guard prevents an indefinite hang.

Both pass; `flutter analyze` 0 errors on the changed files.

## Resume, added and verified

The `.tmp` is no longer thrown away between attempts. `httpDownload` gained an
`{int offset = 0}`; a non-zero offset sends `Range: bytes=<offset>-` and appends.

**The safety rule is the important part.** Resuming is only correct when the remote content has not
changed since those bytes were written, and nothing here stores an `ETag`/`Last-Modified`, so:

- `DownloadUtils.download` passes `resume: true` **only from the second port attempt onward**
  (`getPortsByPrefer(true)` yields `[mixedPort, null]` — proxy then direct, seconds apart, so the
  content cannot have moved).
- `downloadWithPort` takes an explicit `resume` flag defaulting to **false**, so its other caller
  (`auto_update_manager.dart:275`) keeps the old delete-first behaviour.
- When every attempt fails, `download()` deletes the `.tmp`, so **a later run never resumes against
  a file that may have changed.** That is the case a stored validator would be needed for, and it is
  deliberately not attempted.
- If the server answers **200** to a ranged request it ignored the Range and is sending the whole
  file, so the sink is opened with `FileMode.write` and the stale prefix is replaced. Answering 206
  means the prefix is valid and the sink uses `FileMode.append`. Getting this backwards produces a
  silently corrupt file, which is why it is tested.

Verified by two more tests in `test/http_download_stall_test.dart` (4 total, all passing):

1. A ranged request sends `bytes=<offset>-` and the two halves join with the original prefix intact.
2. A server that ignores Range (200) **replaces** the file — asserted by length and content — rather
   than appending to a stale partial.

`flutter analyze` 0 errors on all three changed files.

## The auto-update download gets the same treatment

`auto_update_manager.dart:275` is the other `downloadWithPort` caller and it fetched the **largest
file the app downloads** with the same delete-and-restart behaviour. It now passes
`resume: attempt > 0` across its own port loop.

That one is safe by construction rather than by argument: the code immediately sha256-checks the
result against `_versionCheck.sha256`, so a resumed download that did not reassemble correctly is
**rejected**, not installed. Worth remembering as the reason it was safe to change.

## Audit: no other instance of the deadline-covers-the-transfer bug

Grepped every `.timeout(` in `lib/app/utils/` and `lib/app/modules/`. The remaining sites are
**probes and scans** — `cloudflare_utils.dart`, `dns_direct_probe.dart`, `node_direct_probe.dart`,
`scan_dialer.dart` — where a short deadline is the entire point (measuring reachability). None of
them streams a body. So `httpDownload` was the only place a transfer was capped by a request
deadline, and there is nothing left to fix in this class.

# `HttpUtils` is the APP's client — it has nothing to do with the user's AI agents

Asked directly: *"Does the change you made also apply when agents answer upstream?"* The answer is
**no**, and the reason is worth keeping straight, because it is an easy thing to get wrong.

**`HttpUtils` only ever serves Karing's own operations** — subscription updates, rule-set downloads,
app auto-update, and backup/sync. The user's AI agents (Claude Code, OpenCode, Devin, Cursor…) are
separate processes; their traffic goes *system proxy → Karing's mixed port → core → upstream* and
**never passes through `HttpUtils`**. So no Dart change here can affect agent traffic in either
direction.

**What does cover agent traffic, in both directions:**

1. **The core ESTATS fix** — the dominant cause (89% of failures). It applies to every connection the
   core makes, upload or download.
2. **`interrupt_exist_connections: false`** — direction-agnostic: a node switch no longer tears down
   a live connection, so a long agent stream *or* a long upload survives it.

**There is no upload-direction version of the deadline bug, and that is not an oversight:**

- `httpUpload` has **no timeout at all** — nothing was capping it, so there was nothing to fix. Its
  only caller is `group_helper.dart:3042` (backup/sync), so it is not agent traffic anyway.
- `httpPostRequest` takes an in-memory `String body`, and its race calls
  `waitResponseDone(request, null)`. With `path == null` that helper returns after the response
  **headers**, so the deadline is correctly scoped. **This is exactly why 4 of the 5 `Future.any`
  sites were fine and only `httpDownload` was broken** — it was the only one passing a non-null
  `path`.

**Known asymmetry, deliberately not changed:** `httpUpload` has neither a deadline nor a stall guard,
so a stalled upload waits indefinitely. That is the mirror of what was fixed for downloads. Flagged
to the user and offered; not implemented unasked, since it is backup-only and unrelated to agents.

## 🔴 BUG (now fixed): the app never captured the core's log

`service_core.log` and `service_error.log` were **never created** across the whole run. Root cause:
**sing-box logs to stderr and stdout is empty** — measured 23,799 bytes on stderr vs **0** on stdout,
so the `stdout.listen` → `service_core.log` path could never produce anything, and the stderr path
produced nothing either despite `FileUtils.append` being correct. Why the stderr capture failed is
**still unexplained** and would need the app running to pin down.

**Fix — make the core write its own file** instead of trusting pipe capture:

```dart
final coreLog = kDiagnosticLogging ? PathUtils.coreLogOutputPathIfProbed() : null;
return {'level': …, 'timestamp': true, if (coreLog != null) 'output': coreLog};
```

**The trap that makes this dangerous:** an unwritable `log.output` makes sing-box **die at startup** —
verified: `FATAL start service: start logger: open Z:/…: The system cannot find the path specified`,
exit 1. So the path is **never guessed**: `PathUtils.coreLogOutputPathIfProbed()` returns the directory
only after `logDir()` has already proved it writable (it writes/deletes `.log_write_probe`, and
`app.log` lands there at startup). Verified end-to-end: `check` exit 0, and the core wrote
**12,984 bytes** into `service_core.log` itself. Full suite still 123/123.

## ❌ RETRACTED: the `_windowsStopCore` "4 s stall" claim was wrong

I wrote here that `_windowsStopCore` must burn its full 4 s deadline on every stop because it binds
`mixedRulePort` (3068) to test for release, and 3068 was in Windows' reserved range. **That is false,
and testing it is what proved it.**

A Dart bind test (`ServerSocket.bind(loopbackIPv4, port)`) returned **`3068: bind OK (free)`** — as did
3067 and 3057. Re-checking the reservation showed why:

```
      3068        3068     *        <- before: 3068  3167   (a dynamic block, no `*`)
```

The user had applied the Fix B recipe, converting the Hyper-V/WinNAT **dynamic block** `3068–3167` into
a single **administered** exclusion of 3068. **An administered (`*`) exclusion is bindable** — the
`*`-marked 6037 is actively listening, and now 3068 binds too. So the port-release loop exits on its
first iteration and there is no stall. **No code change was made, correctly.**

**Lesson: an absence/inference claim about runtime behaviour needs a runtime test.** I had read the
code, seen 3068 in a reserved range, and inferred a 4 s stall — a plausible chain that was simply
wrong. `netsh … show excludedportrange` also *changed between checks*, so the earlier snapshot was
stale as well.
