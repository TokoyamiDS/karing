## Vetted SNI + clean-IP candidates — the rule that governs the whole method

User asked for fresher SNI domains and clean IPs from Iranian sources. Result written to
**`docs/sni-clean-ip-candidates.md`**.

### The finding that matters

**The fake SNI must be a Cloudflare-fronted domain.** Measured, not assumed: of 24 popular domains, 11
failed the handshake and **every failure was a domain that is not behind Cloudflare** — Akamai, AWS,
Fastly, CloudFront. A CF edge refuses an SNI it does not serve, and that presents as "no latency, not
working".

So: never pick a domain because it is famous. Resolve it and check the address is inside
`https://www.cloudflare.com/ips-v4`.

### What was vetted

- **13 SNI domains**, all DNS-verified Cloudflare-fronted, all 100% across 3 handshake passes.
  `www.speedtest.net` — the value already configured — passes. The SNI was never the problem.
- **17 clean IPs**, all inside Cloudflare's official ranges, all answering 3 of 3 passes.

### Source notes

- `https://www.cloudflare.com/ips-v4` — authoritative, 14 ranges, always current.- `ehsan7672/sni-spoofing-rustehsa-` → `data/scan-snis.txt` — 720 candidates, a Rust port of
  `@patterniha`'s SNI-Spoofing (same method as this app), pushed 2026-04-20. **Only 248 of 647 are
  Cloudflare-fronted today** — 38% drift. Treat published lists as candidates, never as answers.
- **`vfarid/cf-clean-ips` is stale** — `last_update: 2024-02-10`, no SNI file. Useful for its
  per-operator tags, not for current addresses.
- `mlmvpn/*` are scanner apps, not lists — no static IP/SNI data to harvest.

### Correction: `ips-v4` is the wrong test for "is this Cloudflare"

I used `cloudflare.com/ips-v4` as the filter and it is **not** the right one. That list exists for
**origin whitelisting** — what you paste into a firewall so Cloudflare can reach your origin. It is not
the full edge set.

Cloudflare runs at least two ASes: **AS13335** (mostly in `ips-v4`) and **AS209242 "Cloudflare London,
LLC"** (**not** in it). The user's six configured IPs are all AS209242 — `ips-v4` called them
"NOT in CF range", yet **all six complete a TLS handshake**. Genuine Cloudflare infrastructure the file
doesn't mention.

**Order of authority when checking:**
1. Does the handshake complete? (ground truth — a CF edge accepts an SNI it serves)
2. Is the AS AS13335 or AS209242?
3. `ips-v4` membership — sufficient, **not** necessary. Absence proves nothing.

The SNI verdicts in `docs/sni-clean-ip-candidates.md` were all measured by handshake, so they stand. The
"248 of 647" count used `ips-v4` as a pre-filter and **undercounts**.

### Bottom line for the user's config

Their SNI (`www.speedtest.net`) and all six IPs **work**. The only fault is
`enable_sni_spoofing = False` — the method is configured correctly and switched off.

## In-app speed test on the home screen

User: *"a simple button as home widget … realtime with just a click findout whats my max download or
upload or both max speed"*, then *"so i cant only select for upload speed?"*

The `SpeedTestCard` already existed but only opened a **webview** to `speed.cloudflare.com` — it never
measured anything. Now it measures in-app.

### What was built

- **`lib/app/utils/speed_test.dart`** — pure `dart:io`, no Flutter, so it runs standalone for testing.
  Streams `speed.cloudflare.com/__down?bytes=N` through the mixed port with live byte counting, then
  `POST __up` with incompressible random chunks (zeros would let a middlebox cheat the reading).
  **Time-boxed, not size-boxed** — 12 s per phase, because a fixed byte count is either too small on a
  fast link or stalls forever on a slow one.
- **`SpeedTestMode { both, download, upload }`** — upload-only was an explicit request. The two phases
  cost twelve seconds each, so someone debugging uploads should not pay for a download first.
- **`lib/screens/speed_test_dialog.dart`** — mode chips, a large live Mbps figure, then per-direction
  results with Mbps and MB. Remembers the last mode.
- **Tap** runs it; **long-press** keeps the webview. Nothing was lost.

### No i18n work needed

`meta.download`, `meta.upload`, `meta.all`, `meta.start`, `meta.loading`, `meta.done`, `meta.close`,
`meta.systemProxy`, `meta.local` **all already existed**. So this needed **zero new keys** — no
28-locale pass, and the parity test passes untouched. Check `meta` before assuming new strings are
required; it has 254 entries.

### Verified against the live network, not assumed

```
download  down=1.22  up=0.00  ok=true
upload    down=0.00  up=2.42  ok=true
both      down=3.60  up=20.65 ok=true
```

Each mode reports only its own direction. Live progress climbs as the TCP window opens, which is the
realistic shape.

### A silent failure that testing caught

The first run had `both -> down=0.00, err=""`. The cause: `_download` returned 0 **without an error**
when the status was not 200 or the body ended empty — so a failed phase scored zero and looked like a
result. Phases now carry their HTTP status out and a zero-byte phase sets a real error. The transient
case has not recurred, but it can no longer hide.

**Worth noting for the user:** their upload measured **20x** their download (20.65 vs 1.22 Mbps). That
asymmetry is exactly why upload-only matters to them.

### Reminder

`flutter analyze` needs `meta.*` accessors to exist — but these did, so the generated files were never
touched and `dart run slang` was not required.

## Speed test: cancel added

User: *"theres no cancel for this action."* Correct — the dialog disabled Close during a run, and a
`both` run takes up to 24 s. Committing to that was the only option.

`SpeedTestCancel` (a flag, not a Future race — the phases own their sockets) plus:
- an in-loop check between chunks, and
- a **watchdog** that closes the client, so a cancel lands even when the link has stalled and no chunk
  is arriving to run the check.

`_cancelRun()` flips it and closes the dialog. **Verified: cancelling at 2000 ms returns in 2978 ms**,
not 24 s. `meta.cancel` already existed — no new i18n keys.

**Also fixed while testing:** `HttpClient` honours `HTTP_PROXY`/`HTTPS_PROXY` when no `findProxy` is
set, so the test harness was measuring through this shell's proxy (Karing's, `127.0.0.1:10951`). Now
`findProxy` is always set — `PROXY 127.0.0.1:$port` or `DIRECT` — so the reading is always the path the
dialog claims. A desktop user with a proxy exported would otherwise have measured something else.

## Iran routing did not apply to TUN connections — the core was never sniffing

User: *"the routing for iran seems like not applying to tun connections."* Correct, and the cause was
one missing rule.

### Root cause

`singbox_config_builder.dart` added the `sniff` action **only inside the `enableServerless` block**:

```dart
if (setting.tls.enableServerless) {
  rules.add({'action': 'sniff', 'sniffer': ['tls', 'http', 'quic']});
```

So in normal mode the core never sniffed. That splits the two paths:

| path | what the core sees | what can match |
|---|---|---|
| mixed port (system proxy) | the **hostname**, sent in the request | `geosite-ir` → **direct** ✓ |
| TUN | raw **IP packets**, no hostname | only `geoip-ir` |

Under TUN, Iranian traffic therefore depended entirely on DNS handing back an **Iranian** address — and
with "resolve through proxy" on, anything outside `geosite-ir` resolves through `dns-remote-1`, comes
back as a foreign IP, matches neither `geosite-ir` nor `geoip-ir`, and gets **proxied**. Which is
exactly what the user saw.

Related: the TUN inbound (`SingboxInboundTunOptions`) has **no `sniff` field**, and in sing-box 1.11+
the inbound `sniff` option is gone anyway — the `sniff` **action** is the only mechanism.

### Fix

The sniff action is now added **near the top of the route rules**, before anything domain-based:

```dart
if (tunMode || setting.tls.enableServerless) {
  rules.add({'action': 'sniff', 'sniffer': ['tls', 'http', 'quic']});
}
```

The late copy inside the serverless block was removed. **Position is the whole point** — a sniff rule
placed after the domain rules is as useless as no rule at all, because `sniff` is not final and only
affects rules that come *after* it.

### Test: `test/tun_sniff_before_iran_rules_test.dart`

Four tests: sniff exists under TUN, its index is **less than** the `geosite-ir` rule's, it carries no
`outbound` (which would make it final and bypass everything below), and it is absent when neither TUN
nor serverless is active.

**Verified it catches the bug**: with the condition forced to `false`, 3 of 4 fail. A test that passes
proves nothing until you watch it fail.

### API notes for this codebase

- `SingboxConfigBuilder.route(...)` returns a **Map** directly — not a `ReturnResult` like `dns()`,
  which has `.error` / `.data`.
- `iranMode` is **derived** (`iranModeOverride ?? regionCode == "ir"`) and has no setter. Tests set
  `setting.iranModeOverride`.
